# OwnBot QA report — 2026-10-29

## Local CLI and daemon workflow

**Result: PASS, 50 checks.** The test used the built CLI and daemon, a temporary data directory, and deterministic HTTP model and MCP fixtures bound to loopback. The run exported 580 audit records, including 550 agent creations used to cross the 500-record page boundary.

Commands run from the repository root:

```sh
node --check scripts/test-local-workflows.cjs
OWNBOT_BINARY="$PWD/bin/ownbot" \
OWNBOTD_BINARY="$PWD/bin/ownbotd" \
node scripts/test-local-workflows.cjs
```

The script checks these workflows:

- Empty `ownbot inspect check --json` returns six information-only metadata checks without contacting either provider fixture.
- Model add and capability probe use the local OpenAI-compatible fixture. The probe records all four capabilities.
- MCP discovery and connection expose the fixture tool. Diagnostics warn and exit nonzero when an enabled agent lacks the matching MCP-server allowlist entry; adding the binding removes the warning. Both diagnostic runs remain metadata-only.
- A requested write waits for approval with zero fixture dispatches. Approval followed by `ownbot inspect runs resume` dispatches the fixture write once. A second write is denied and resumes as failed without dispatching it.
- Audit export follows every page, is newest-first with unique IDs, and supports exact run and event filters. It excludes the argument/result sentinels and retains SHA-256 hashes alongside redaction markers. The exported file is mode `0600` on this macOS run.
- With the test daemon stopped, `ownbot inspect check --json` exits nonzero and preserves six `unknown` checks in valid JSON.

The owner token and database live only under a random temporary directory, which the script removes during cleanup. The daemon uses an ephemeral loopback port; CLI calls pass the same temporary directory explicitly. The child processes receive the existing home-directory value unchanged because the Go runtime needs it to determine the platform home, while `OWNBOT_DATA_DIR` and `--data-dir` direct OwnBot state to the temporary fixture. No user daemon, service, `~/.ownbot` state, real provider, or real MCP server is used. The one approved write is captured by the local fixture.

## Harness corrections during this run

- Fixture servers share the Node event loop, so CLI subprocesses use asynchronous `spawn` with bounded timeouts. A synchronous subprocess call would prevent the fixtures from answering requests.
- The first resume invocation used unsupported `ownbot runs resume` syntax and stopped after 30 checks with `unknown command "runs"`. The harness now invokes `ownbot inspect runs resume`; the complete fresh run passed all 50 checks.
- An earlier startup attempt omitted the home-directory environment and the daemon failed its readiness check. The harness now passes through the host value unchanged and isolates app state with the explicit temporary data directory.

These were harness setup issues; no product-code workaround was needed for them.

## Review fixes before publication

- Removed the silent 500-event export ceiling and the stale claim that tool-call audit history was unavailable.
- Export validates exact run/event filters and descending cursors, including when an older daemon ignores them. Bad pages are rejected before being written. Tests cover bounded cursor failure, no mismatched-page stdout, and preservation of existing output files.
- Output files are replaced only after every page succeeds. Unix mode and atomic-replacement claims are explicitly scoped; metadata such as caller-supplied idempotency keys can still contain private data.
- Diagnostics preserve MCP permission warnings, distinguish disabled/tool-free setups from mismatches, and report missing/null metadata as unknown. Tests cover missing model selections, disabled search toggles, MCP bindings, and legacy binding visibility.
- Inspection help no longer advertises a working logs API. No logs endpoint was added.

## Boundaries

This local workflow verifies the built CLI and daemon against deterministic loopback fixtures. It does not validate live model providers, real MCP servers, OAuth credentials, target hardware, OS service installation, release packaging, or deployment. Physical-device pairing, cellular access, fresh target-hardware installs, live account integrations, service installation, and signed install/update/rollback remain unverified. Passing these fixtures does not complete the product release gate.
